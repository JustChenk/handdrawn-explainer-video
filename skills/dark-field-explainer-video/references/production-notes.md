# 生产笔记（Production Notes）

## 1. 实测数据

| 项目 | 结果 | 备注 |
|---|---|---|
| 渲染速度 | **≈ 21 fps**（720 帧 / 30fps / 34 秒） | 纯矢量 + 文字动画几乎不吃性能 |
| 长片实测 | **≈ 25.8 fps**（Ep00 v1.0.0：4770 帧 @30fps → 190s） | 帧数多时略快于短样片；`frames/` 833 MB |
| 对比手绘线稿 | 明显更快 | 线稿描边 + 抖动是主要开销 |
| 单帧 JPEG 体积 | 约 250 KB（1920×1080, q92） | 720 帧 ≈ 187 MB，记得渲完清理 `frames/` |
| 成片码率建议 | `-b:v 8M` | 参考片实际用了 10.9 Mbps |

**成本结论**：这类视频可以放心用 SubAgent 批量生产，不必像手绘那样省着排队。

## 2. 踩过的坑

### 2.1 rAF 抢帧（最高频，症状最隐蔽）

**症状**：`--test "4.5,12.5,20.5"` 抽三个时间点，得到三张几乎相同的画面。

**原因**：工程 HTML 同时当"浏览器预览页"和"渲染源"。实时的 `requestAnimationFrame`
循环会把宿主 `renderFrame(t)` 设好的状态覆盖掉——宿主要第 12.5 秒，rAF 却把画面拉回此刻。

**解法**（模板已内置）：

```js
window.renderFrame = t => { window.__hostDriven = true; frame(t); };
(function loop(){
  if (!window.__hostDriven) frame((performance.now()/1000) % DURATION);
  requestAnimationFrame(loop);
})();
```

宿主接管后 rAF 立刻让位。已排队的回调也会因首行 return 而不再覆盖。

> `precheck.js` 会强制校验 `__hostDriven` 与 `renderFrame` 同时存在。

### 2.2 幕透明度互相污染

若对三幕都用「当前幕的 p」去算透明度，非当前幕会拿到错的值（例如 `p=0.5` 时幕 1 也被算成全不透明，
于是三幕叠在一起）。

**解法**：每幕按**自己的局域时间**独立算透明度，幕外自动归零：

```js
const sceneOp = p => easeOut(p/.04) * (1 - clamp((p-.94)/.06));
S1.style.opacity = sceneOp((t - SEC[0]) / LEN);
S2.style.opacity = sceneOp((t - SEC[1]) / LEN);
S3.style.opacity = sceneOp((t - SEC[2]) / LEN);
```

### 2.3 流场粒子的确定性

逐帧渲染不能依赖"上一帧残留"，必须能被任意跳播重演。用固定步长推进：

```js
while (flow.simT + 1/30 <= target + 1e-6 && guard++ < 900) stepFlow();
```

跳播跨度 > 0.6s 时先 `resetFlow()`。**guard 必须有**，否则 time 一旦倒退会死循环。
注意：正常逐帧渲染（t 递增 1/30）时每帧只补 1 步，开销极小；只有抽帧跳播才需要重演。

**配套要求：`resetFlow()` 必须用固定种子**重建粒子与随机序列。若用 `Math.random()`，
每次重演的初始分布都不同 → 抽帧看到的画面和全量渲染对不上，而且同一时间点渲两次也不一样。
模板内置 `mulberry32(20261014)`，把种子连同随机序列一起存进 `flow.rnd` 供重生复用。

### 2.4 流场"卷成涡核"

第一版把基角偏移设成 1.42 rad（≈81°，近乎纯切向），配合 0.030 的长拖尾。
短时间看没问题，但幕长 8s 以上的话粒子会持续绕圈、层层叠加，
最终在画面中心堆出一个明显的螺旋涡核 —— 完全丢掉参考片那种"发丝飞散"的观感。

**修正**：基角偏移降到 **1.05 rad**（补足径向分量）、清屏 alpha 提到 **0.042**（缩短拖尾）、
重生区从 ±150px 扩到 ±310px（避免快速堆成一点）。

> 教训：流场参数要**按最长的一幕**来调，不能只测开场那两秒。

### 2.5 幕时长改了但渲染参数没改

新增一幕却忘了改 `--dur` → 尾部的幕根本没被渲染出来。
**`precheck.js` 接受第二参数做交叉校验**：

```bash
node precheck.js video.html 168     # 和 __meta.duration 对不上就报错
```

### 2.6 「空洞幕」返工（v1.0.0 成片的通病）

**症状**：成片中后段出现「纯黑底 + 孤立几行文字」的幕——单看每一幕都"符合极简"，
连起来看却越来越空，观众正是在这里流失（159s 实测成片的完播掉落点与这些幕重合）。

**根因**：v1.0.0 只规定了幕内元素的登场时序，没有规定**一幕必须有几层**，
于是大量产出没有背景纹理层的幕。v1.1.0 起已固化为硬规则 ⑧。

**解法**：执行三层结构纪律——每幕 ≥2 层（背景纹理层 + 前景信息层）。
三层分工、组件（点阵网格 / 微光条目卡）与压场渐晕见 `style-spec.md` §5；
「空洞幕」已列入反面清单（`style-spec.md` §9）；分幕阶段按幕式选好 L1 背景
（见 `scene-patterns.md` 各幕式的背景层说明）。抽帧目检时把"有没有纯黑底孤立文字幕"
当作必查项（SKILL.md 阶段 5）。

### 2.7 焦点大字「黑字橙晕」伪发光（v1.1.0 Ep01 实战撞上）

**症状**：成片里部分幕的焦点大字（−42%、约 −60%、1.15 万人……）呈**暗红浮雕**而非饱满亮橙——
字身几乎是黑的，只剩 glow 阴影的橙边。对比幕里的赢家数字却正常亮橙，一集之内两种焦点观感。

**根因**：新写的焦点大字 class（`.num7` / `.numSmoke` / `.numVest` 这类每幕自定义的定位 class）
**漏写 `color`**。CSS 默认 color 继承链到头是浏览器默认的**黑色**——`.glow-r` 的 text-shadow
照常生效，于是渲染出「黑字 + 橙晕」的伪发光。对比幕的 `.hbig` 因为有
`.half.R .hbig{color:var(--accent-lo)}` 这类显式声明所以没事。
**渲染前完全看不出**（静态看不见颜色缺失的后果），一渲染 4680 帧才暴露，返工成本整条渲染管线。

**解法**：
1. **写法定式**：每个焦点大字/焦点元素的定位 class 必须在同一行 CSS 里显式 `color:var(--accent-lo)`（或 glow-w 配白字），不许依赖继承。写一个新幕的焦点时把 color 当作定位四件套（left/top/size/color）之一。
2. **precheck 已加静态检查**（v1.1.0 起）：`glow-r/glow-w` 元素的 class 链上找不到任何显式 `color` 声明 → ERROR `GLOW_NO_COLOR`。
3. 抽帧目检必查项：**每个「单焦点大字」幕至少看一帧焦点数字的颜色饱和度**，暗红浮雕 = 本坑。

### 2.8 渲染/编码赛跑 → frames/ 新旧混杂，成片幕序错乱（Ep01 实战撞上）

**症状**：成片幕序错乱且**错位不单调**——t58 显示 86s 幕的内容、t80 显示 96s 幕的，
t33/t70 却又正确；ffprobe 帧数/时长完全正常。极难诊断：看起来像「场景调度 bug」，
但工程源码探针渲染（`--test`）完全正确。

**根因**：重渲**没有先清空输出目录**，且**编码在渲染尚未结束时启动**。frames/ 里混着
两次写入的帧（实测 600 帧 @06:42 + 4080 帧 @06:51-54 两个 mtime 簇），编码按文件名
顺序读到混合序列——内容时间轴被撕碎。工程本身没有任何问题。

**诊断手法**（一分钟实锤）：

```bash
stat -c '%y' frames/f*.jpg | cut -c12-16 | sort | uniq -c
# 正常：只有一个连续时间段的单簇；出现两个簇 = 目录被污染，成片作废
```

**解法**（三条纪律）：
1. **重渲前先删整个 frames/ 目录**再渲染（注意 shell 的 cwd 别停在目录里，
   Windows 会报 `Device or resource busy` 删不掉——cd 出去再删）。
2. **渲染与编码严格串行**：等渲染任务退出（后台任务收完退出通知）再起编码，
   绝不「渲染完自动接力编码」地并行排队。
3. **渲染完成后、编码前**验两件事：帧数 = `--dur × fps`；mtime 单簇。
   两项过了才编码。

### 2.9 同一集跨风格重制：内容照抄，时长必然膨胀（Ep00 手绘 74s → 暗场 159s）

**症状/疑问**：把手绘版已完成的同一集（74s / 7 幕）用本风格重做，成片变成 159s / 13 幕，
看起来像"注水"，用户第一反应通常是"是不是节奏拖了"。

**根因**：不是注水，是风格语法决定的——
- 本风格「一屏只讲一件事」（规则 ⑤），手绘版一屏塞下的贴纸墙，在这里必须拆成多个独立幕；
- 列表 / 片名墙类幕**必须留静止阅读时间**（每条 ≥1.2s，见 `scene-patterns.md` 档案墙幕），
  手绘版那种"快闪预告"节奏在本风格里不成立；
- 幕内元素错峰 0.15~0.3s 登场，本身就比手绘动画慢。

**对策**：
1. **动手前先告知用户时长会翻倍**，并同步 `系列规划.md` 之类有"单集时长"承诺的文档，
   否则系列规格对不上（正式纳入需走一次 C 级变更）；
2. 片名墙 / 列表幕**不进 A 板加速流程**——加速会毁掉可读性，
   已在 `bgm-beat-align` SKILL.md 决策树中列为 A 板否决信号；
3. 内容、口径、制作红线**逐字继承**原版，只重做视觉结构。不要顺手改文案：
   两层变更叠在一起，日后无法判断差异来自内容改动还是风格改动。
4. 重制 v1.0.0 旧片时，顺带按 2.4（涡核）/ 2.6（空洞幕）复检一遍——这两个正是旧版的通病。

## 3. 与系列其他 skill 的边界

| 事项 | 处理 |
|---|---|
| 逐帧渲染 / 编码 | **复用** `handdrawn-explainer-video/scripts/`，不要复制一份（单一事实源） |
| 字体 | 本风格**只用系统字体**，不需要 `assets/fonts/`（这是相对手绘 skill 的一大简化） |
| 封面 | 用 `douyin-cover-generator`，但必须切到暗色 + 橙强调，别沿用纸面手绘那套模板 |
| 系列拆集 | >180s 或多个心智模型时先过 `series-video-planner` |
